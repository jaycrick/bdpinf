# Evaluation: rumdl, panache, and quartodoc → great-docs

## Context

The project currently has **no Markdown linter** anywhere in its toolchain --- the existing
quality stack (`ruff`, `isort`, `basedpyright`, `toml-sort`, `lintquarto`) covers Python and TOML
but not the \~30 prose `.md` files or the prose portions of the 58 `.qmd` notebooks.
The API
reference is generated by **quartodoc**, driven by the `quartodoc:` block in `_quarto.yml`
(`_quarto.yml:128-201`), producing 28 auto-generated `reference/*.qmd` stubs across 8 sections
(Core model, Mathematical functions, Input validation, Inference, Simulation, Visualization,
Analysis, Data pipeline).

The user asked whether adopting **rumdl**, **panache**, and migrating **quartodoc → great-docs**
is a good idea.
This document records the findings and verdicts, including what was learned by
actually running each tool against this repository, not just reading their docs.

## Verdict (short version)

  | Tool                         | What it is                                                                                                                                                                                                                           | Verdict                                                                                                                                                                                                                                                                                                           |
  | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | **rumdl**                    | Rust Markdown linter/formatter (rvben/rumdl), ~97% markdownlint-compatible.                                                                                                                                                          | **Rejected.** Its default scan picked up `.qmd` files alongside `.md`, and its auto-fixer **corrupted LaTeX math**: lines like `\ell_t(\theta_0)` inside `$$...$$` blocks got rewritten into `## \ell_t(\theta_0)` ATX headings. It does not understand Pandoc/Quarto math or executable-chunk syntax. See below. |
  | **panache** (jolars/panache) | LSP + formatter + linter purpose-built for Pandoc/Quarto/RMarkdown markdown (fenced divs, citations, grid tables, math). PyPI package `panache-cli`.                                                                                 | **Adopted**, for both `.md` and `.qmd`, scoped to lint + format with a documented config (see below). Found and worked around one real formatter bug; the linter is clean.                                                                                                                                        |
  | **great-docs**               | Posit's newer documentation-site generator, billed as quartodoc's successor. Auto-discovers a Python package's API, adds a landing page, CLI reference, quality tools (`lint`/`proofread`/`check-links`), and `llms.txt` generation. | **Adopted, hybrid.** Full parity for the API reference; replaces quartodoc. Cannot absorb the executable notebook site (no cache/biblatex support). CLI reference works via a small Typer→Click shim — see below.                                                                                                 |

## rumdl: why it was rejected

rumdl's default file-type detection is not limited to `.md` --- running `rumdl check .` against
this repo touched `.qmd` notebooks.
Its auto-fixer (`--fix`) misidentified backslash-prefixed
display-math lines inside `qmd_scripts/validation/single_epoch/08_asymptotic_consistency_llm.qmd`
as ATX headings and rewrote them, e.g. turning

```text
\ell_t(\theta_0)
=
\log p_\theta(Z_t\mid t)
```

into

```text
## \ell_t(\theta_0)

=
\log p_\theta(Z_t\mid t)
```

silently destroying the equation's structure.
Even after scoping rumdl strictly to `*.md` via
`include = ["*.md"]`, this is still a tool with no concept of Pandoc/Quarto math or executable
chunks --- a real risk for a project where `.qmd` files mixing prose, LaTeX, and Python is the norm,
not the exception.
It was dropped in favor of panache, which is purpose-built for that mix.

## panache: what worked, what didn't, and the configuration that resulted

panache's linter (`panache lint`) is Quarto/Pandoc-aware and, after configuration, found **zero**
genuine issues across all 60 `.md`/`.qmd` files.
Two of its 20 built-in rules needed disabling
because they are false-positive-prone for this specific codebase:

- **`undefined-references`** --- flags any `[...]` that *could* be a Pandoc shortcut reference link.
  This fires constantly on this project's bracket notation: Keep-a-Changelog `[Unreleased]`
  headers, Python slice/index notation (`x[0]`, `non_spine_component[1:]`), and interval notation
  (`[700, 2020]`).
  21 of 21 hits in this repo were false positives.
  - **Gotcha discovered**: the CLI's own diagnostic note is wrong --- it tells you to set
    `[lint.rules] undefined-reference-label = false`, but the real config key is
    `undefined-references`.
    The hyphenated `-label` variant silently does nothing (no error, no
    effect).
    Filed away here so the next person doesn't lose time re-discovering this.
- **`missing-chunk-labels`** --- flags every executable `{python}` chunk without `#| label: ...`.
  261 of 282 baseline hits.
  The project's notebook convention (`CLAUDE.md`'s "Per-notebook
  conventions") doesn't currently require chunk labels outside the timing bracket, so enforcing
  this now would be an unrelated mass edit across \~30 notebooks.
  Disabled for now; worth
  revisiting if the project later adopts labelled chunks as a convention.

panache's **formatter** (`panache format`) is more invasive than the linter by default:

- `wrap = "reflow"` (the default) hard-wraps every paragraph at `line-width` (80 cols).
  This
  project's prose is intentionally not hard-wrapped (see any file in `docs/design/`), so the
  default would rewrite nearly every line of every prose file.
  Initially set to `wrap = "preserve"` (no reflow at all); later switched to
  `wrap = "semantic"` (one clause/sentence per line, à la SemBr) so future diffs are scoped to
  the sentence that actually changed instead of an entire reflowed paragraph.
- The `smart` extension (on by default) rewrites literal em-dashes (`—`) to `---`; accepted as-is
  (see the config discussion below for a config mistake this caused along the way).
- Markdown tables get realigned to fixed-width columns regardless of `wrap` --- there is no config
  key to disable this.
  It's cosmetic (output renders identically) and was accepted as-is.
- **Bug found**: a single file, `docs/design/PLOTLY_TO_ALTAIR_EVALUATION.md` (since removed, its
  decision having been acted on), hit a genuine
  formatter idempotency bug --- `panache format` is supposed to satisfy
  `format(format(x)) == format(x)`, but a bold span (`**...**`) that crossed a wrapped line inside
  a `>` blockquote caused the formatter to prepend an extra `>` to one line on every run, growing
  without bound (`>` → `> >` → `> > >` → ...).
  Confirmed via
  `panache debug format --checks idempotency .` that this was the **only** file affected across
  the whole repo.
  Fixed by manually joining the bold span onto one physical line inside the
  blockquote (a one-line content edit, not a config workaround) --- re-verified clean afterward.

Resulting `panache.toml` (repo root):

```toml
[format]
wrap = "semantic"

[extensions]
smart-quotes = true

[formatters]
python = ["isort", "ruff"]

[lint.rules]
undefined-references = false
missing-chunk-labels = false
```

`extensions.smart-quotes` normalizes curly quotes/apostrophes only --- unlike the broader `smart`
extension, it does not also touch dashes or ellipsis.
`smart` itself is left at its default (on),
so em-dashes (`---`) still get rewritten to `---` by the formatter; an earlier draft of this config
set `smart = false` specifically to preserve real em-dashes, but that protection was deliberately
dropped --- em-dash normalization is accepted.
(A first attempt at this swapped the key to the
non-existent `smart-quotes = true` while *also* deleting `smart = false`, which silently
re-enabled em-dash mangling across 45 files without erroring --- `smart-quotes` and `smart` are
different keys, not a rename.
Caught by diffing em-dash counts against the previous commit before
it was committed.)
`[formatters] python = ["isort", "ruff"]` shells out to the project's existing
linters when panache formats Python code chunks inside `.qmd` files.

Wired into `.pre-commit-config.yaml` (`panache-lint --fix`, `panache-format --check`, mirroring
the project's existing convention where checkers auto-fix and formatters fail-and-report) and into
the CI `lint` job.
A one-time baseline pass (`panache format .` + `panache lint --fix .`)
was run
and reviewed file-by-file before being wired into pre-commit/CI.

## great-docs: architectural tension

`_quarto.yml` is not a thin docs config --- it drives a full research website:

- 9 navbar menus (`_quarto.yml:26-104`) covering Reference, Data Exploration, Single/Multi-Epoch
  Analysis, Bayesian Analysis, three Validation tracks, and Docs.
- 30 **executable** notebooks under `qmd_scripts/core_analysis/**` and `qmd_scripts/validation/**`
  that run real inference code, not static prose.
- Global cell caching (`execute.cache: true`), biblatex citations (`cite-method: biblatex`), and
  a custom HTML theme (flatly + MathJax + code-fold).

great-docs generates its **own self-contained Quarto project** from a `great-docs.yml` config and
does not consume an existing `_quarto.yml`.
It is designed to own "a package's documentation
site," not to be grafted onto an existing 30-notebook research website.
This is the central risk:
migrating naively could mean either (a) losing the notebook site, or (b) running two disconnected
Quarto projects side by side, which is worse than the status quo.

This is why the great-docs migration was **spike-gated** rather than committed outright.
The spike
(running `great-docs build` against this repo, not just reading docs) confirmed the risk was real:

- **API reference: works, full parity.** A `reference:` config in `great-docs.yml` mirroring all 8
  quartodoc sections (Core model, Mathematical functions, Input validation, Inference, Simulation,
  Visualization, Analysis, Data pipeline) built cleanly --- same 28 content pages, and the
  `BirthDeathProcess` class page documents its 13 methods *and* 15 properties inline (quartodoc
  only listed methods).
  One harmless warning per build: dynamic introspection fails for symbols
  not re-exported at the package's top level (e.g. `inference.fitting.fit_birth_death_processes`),
  and falls back to static analysis successfully.
- **CLI reference: broken out of the box, fixed with a one-line shim.** Enabling
  `cli: {module: bdpinf.cli, name: app}` crashes the build with
  `AttributeError: 'Typer' object has no attribute 'allow_extra_args'` --- great-docs's CLI doc
  generator expects a raw `click.Command`, and `bdpinf.cli:app` is a `typer.Typer()`
  instance, not supported directly in v0.14.0.
  Typer wraps Click internally, so
  `typer.main.get_command(app)` produces exactly the `click.Command` great-docs wants, with no
  behavior change to the CLI itself.
  Added as `bdpinf.cli.click_app` (a single module-level
  line, not used anywhere else) and pointed `great-docs.yml`'s `cli.name` at it.
  Rebuilt clean,
  generating a full nested reference (`reference/cli/`, including the `ntvmr` subcommand group and
  all five of its leaf commands) --- confirmed by inspecting the generated HTML/markdown output.
- **`pypi: false` crashes the build --- a real upstream bug, not a config mistake.** Documented as a
  normal option (suppress the auto-generated "View on PyPI" margin link), but combined with this
  project's `CITATION.cff` it raises `UnboundLocalError: cannot access local variable   'package_name'`.
  Root-caused in `great_docs/core.py`'s `_build_metadata_margin()`: the local
  `package_name` is only assigned inside an `if pypi_setting is not False:` block (core.py:9796),
  but a later, unconditional branch for the citation link (core.py:10124,
  `pkg_display = package_name or ...`) reads that same variable regardless of whether the `pypi`
  block ran --- so any project with both `pypi: false` and a citation file hits this.
  Left `pypi` at
  its default; not worth a local source patch for one cosmetic link.
- **Executable notebook site: not viable.** Confirmed by reading the full `great-docs.yml` schema
  (`great-docs config` dumps every documented key) --- there is no `execute.cache`, `bibliography`,
  or `cite-method` equivalent anywhere in it, and great-docs's own docs state plainly that its
  generated `_quarto.yml` is fully owned by the tool and manual edits are overwritten on every
  build.
  There is no path to carrying the 30 executable notebooks' caching and biblatex citations
  into a great-docs-owned project.

## Decision

1. **rumdl** --- rejected; see above.
2. **panache** --- adopted for both `.md` and `.qmd`, lint + format, wired into pre-commit and CI.
3. **great-docs** --- **adopted in hybrid form**, per the spike above: great-docs now owns the API
   reference (`great-docs.yml`, replacing quartodoc and the auto-generated `reference/` directory)
   and the package landing page, including a CLI reference (via the `click_app` shim in
   `bdpinf/cli.py`); `_quarto.yml` continues to own the 30-notebook research site
   unchanged otherwise (quartodoc's `quartodoc:` block, `reference/*.qmd` render glob, and
   `reference/_styles-quartodoc.css` removed from it).
   This means **two separate sites** rather
   than one unified Quarto site --- accepted as the cost of dropping quartodoc, with no navbar
   cross-linking between them.
   CI was **not** changed to build the great-docs site: it requires the Quarto CLI binary, which
   CI does not currently install for any purpose (the existing notebook site isn't built in CI
   either) --- adding Quarto-CLI setup to CI is a separate, larger piece of infra than this migration
   needed.
